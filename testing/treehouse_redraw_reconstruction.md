## Read-only execution trace

`build_trace_core.py` compiles a separate DLL from the pinned core's existing
objects, replacing only the normal CPU object with an observer. It neither
overwrites the original capture DLL nor modifies original game instructions,
RAM, emulated cycle charges, timers or drawing code. Instruction-entry probes
record selected function calls, registers, stack arguments and the precise
emulated millisecond clock. The libretro virtual game-RAM address map is converted
back to physical addresses before configuring probes.

Only addresses that distinguish the redraw stages are observed. Trace buffers
are drained while the deterministic frontend callback holds the worker. Buffer
overflow is a hard error. The probe also reads the current indexed framebuffer
and VGA timing configuration at that same boundary.

## Snapshot-boundary correction

An early expanded probe run was one emulated video frame ahead immediately
after restoration. Source inspection identified an independent harness race:
`retro_run` releases the worker for the next frame; `retro_unserialize` pauses
and resumes that worker, which may still be partway through the pending frame.
The next callback then depends on host scheduling.

The tracing harness now calls the public `retro_get_system_av_info` before
restore/save. In the pinned core this calls `TCM_FINISH_FRAME`, leaving the worker
held at the frame boundary. Repeated captures and a probe-disabled control
then agree exactly. Historical captures remain preserved. The old general
capture helpers have not been silently changed or their evidence relabeled.

The experimental `nature-redraw-trace-c` run is not accepted timing evidence.

## Why an instantaneous screen cannot match every callback

This pinned DOSBox configuration uses mode 3 (`M_VGA`) and draw mode 0 (`PART`):

- A 14.2680641955 ms video period, about 70.0863 Hz.
- Four 50-row reads per frame, 3.1777557100 ms apart.
- The first part is read one part interval after `framestart`.

See pinned core `vga_draw.cpp`, `VGA_VerticalTimer`'s `PART` branch and
`VGA_DrawPart`. The framebuffer can change between those four reads. A published
video frame can therefore contain upper rows from one completed drawing and
lower rows from the next. In 26 callbacks of the traced turn, the published RGB
image differs from the live framebuffer read at callback completion.

This describes the reference emulator's presentation schedule; it is not a
claim that physical VGA hardware reads the screen in four chunks.

## Verified component

`OriginalScanout.commit(milliseconds,pixels)` retains an immutable framebuffer
snapshot. `present(frameStart)` reads the applicable snapshot for each horizontal
part and releases history that future frames cannot use. Invalid geometry,
backward clocks and writes into an already presented interval are rejected.

`verify_scanout.py` renders the actual question through `NatureQuiz`, loads those
independently generated pixels, and pairs its 24 authored display commits with
the 24 original copy-completion timestamps. The last authored display repeats
the previous visible state. Every callback 2115..2420 is compared over all 64,000
RGB pixels, with no shifts, exceptions or pixel tolerance. The commit schedule
is explicitly fixture data for this component check, not a runtime shortcut.

Result: 306/306 callbacks and 5 component checks pass. The instantaneous baseline
matches 291/306. Report: `output/treehouse/scanout-component-b/report.json`.
